# Single-Ledger Warm Ledger UI Design

Date: 2026-07-07

## Goal

Redesign Cashier as a fully single-ledger personal bookkeeping product with a unified, quiet, warm visual system.
The redesign must cover the main workspace tabs, settings, login, task feedback, shared UI primitives, route
semantics, and development access.

The product should feel like a long-lived personal ledger tool: calm, clear, slightly warm, and individual, without
becoming decorative, retro, paper-textured, or ChatGPT-like.

## Product Decisions

- Cashier is a single-ledger product. Users do not create, switch, select, or manage multiple ledgers.
- The app entry is the product workspace, not a ledger chooser. After login, users land in the single workspace.
- The current four top-level work areas remain: `stream`, `details`, `stats`, and `settings`.
- Service credentials remain, but they become account-level automation credentials for the only ledger.
- Existing non-default ledgers do not enter the redesigned experience.
- Settings use workflow grouping:
  - Appearance and language
  - Bookkeeping rules
  - AI parsing
  - Automation
  - Account and data
- Development builds need a safe local-only way to open the workspace and inspect all four tabs without configuring
  email delivery through Resend or completing the OTP login flow.

## Non-Goals

- No multi-ledger UI preservation in the new product experience.
- No enterprise accounting, collaboration, approval, audit, bank-sync, or ERP-style workflows.
- No marketing landing page. The first authenticated surface is the usable app.
- No decorative theme that relies on paper textures, skeuomorphic aging, handwritten fonts, stickers, or heavy
  illustration.
- No production auth bypass. The development entry must not work in production or preview deployments.
- No change to API v1 response contracts in this design unless a later implementation plan explicitly scopes it.

## Current State

- The protected home page currently resolves or creates a ledger and redirects to `/ledger/[id]`.
- The primary workspace is rendered by `LedgerPageClient` under `src/app/[locale]/(protected)/ledger/[id]/page.tsx`.
- Tabs are represented by the query parameter `tab` and currently include `stream`, `details`, `stats`, and
  `settings`.
- The project uses Next.js App Router, React, Tailwind CSS, shadcn/Radix-style primitives, Lucide icons, TanStack
  Query, Auth.js, and OTP email login.
- Existing UI documentation describes a very minimal AI-tool style with white surfaces, gray borders, and a single
  green primary color. This contributes to the current generic ChatGPT-like feeling.
- `stream` already has a cleaner toolbar boundary through `LedgerEntriesToolbar`.
- `details` duplicates more toolbar and batch-action structure inline.
- `stats` has useful data surfaces, but some visual values are hardcoded, including heatmap colors and currency
  formatting.
- `settings` mixes email, service credentials, export, danger actions, category management, and sign-out in a way
  that no longer matches the single-ledger model.

## Target Product Model

### Single Ledger Semantics

User-facing surfaces must never ask the user to pick a ledger. The word "ledger" may remain in domain code where it
represents the persisted internal data scope, but the user experience should speak in terms of "your book", "entries",
"automation", "rules", and "data" rather than "current ledger" or "ledger selection".

The implementation may keep an internal default ledger id as a compatibility boundary. That id remains useful for:

- existing database rows;
- tenant isolation;
- existing APIs and server actions that require a scope id;
- local file paths and source-document ownership;
- service credential compatibility.

The compatibility boundary should be centralized. New UI components should receive a resolved single-ledger context
from the workspace shell or bootstrap query instead of independently resolving ledger ids.

### Routing

The product target is direct entry to the workspace from `/`.

Because the current app uses `next-intl` with `localePrefix: "always"`, implementation may internally render through
`/[locale]`. Product navigation, login redirects, and generated app links should still treat the workspace as the root
experience and must not generate `/ledger/[id]` links.

Required target behavior:

- `/` resolves through locale middleware to the workspace route.
- `/{locale}` renders the workspace directly for authenticated users.
- Login success redirects to the workspace root, not `/ledger/[id]`.
- Historical `/{locale}/ledger/[id]` routes redirect to `/{locale}` while preserving meaningful query parameters such
  as `tab`, period, and filters where possible.
- New deep links use root-level query state, for example `/?tab=details` or the locale-prefixed equivalent generated by
  the routing helpers.

### Default Ledger Data Strategy

The redesigned experience reads and writes only the user's main/default ledger. If a user has legacy multiple ledgers,
the implementation should select the existing default ledger or create one if none exists. Other ledgers remain in the
database but do not appear in the new UI.

The implementation plan should decide whether to enforce a single default ledger through a helper such as
`resolveSingleLedgerForUser`. The design requirement is that every new workspace request goes through one such boundary
instead of passing arbitrary route ids from the browser.

## Development Access

Development work should not require configuring Resend or receiving email codes just to view and test the workspace.

Add a development-only entry mode with these rules:

- It is disabled by default outside local development.
- It requires an explicit environment flag, for example `DEV_AUTH_BYPASS=true`.
- It is rejected when `NODE_ENV === "production"` regardless of the flag.
- It creates or reuses a deterministic local development user, for example `dev@cashier.local`.
- It creates or reuses that user's single default ledger through the same single-ledger boundary as normal auth.
- It gives the browser a real Auth.js-compatible session or an equivalent protected-layout-compatible session path.
- It redirects to the root workspace after activation.
- It is visibly marked only in development, for example a small "Dev session" account-menu line, not a production UI
  affordance.
- It must not weaken API v1 bearer credential authentication.

Preferred implementation shape:

- Add a local-only credentials provider such as `dev` to `src/auth.ts` only when the runtime guard allows it.
- Add a dev-only server action or route used by the login page button, not a public unauthenticated production route.
- Render a small "Continue as dev" button on the login page only when the public dev flag allows it.
- Keep OTP login as the only production interactive login method.

Alternative implementation shape, acceptable if Auth.js provider composition makes runtime provider toggling awkward:

- Add a dev-only route handler that provisions the dev user and sets a session through the same session primitives used
  by Auth.js.
- The route must still be guarded by the same local-only checks and must not exist as a production feature.

Development access must be tested by proving the flag is required and production rejects the bypass.

## Visual Direction

### Design Personality

The visual direction is warm personal ledger, with a small receipt or bookkeeping influence expressed through layout,
grouping, alignment, and numbers rather than decoration.

The app should avoid:

- generic AI chat surfaces;
- oversized rounded inputs as the main visual metaphor;
- large pure-white panels floating on pure-white pages;
- one-note beige, brown, orange, purple, or slate palettes;
- decorative paper textures or vintage styling;
- large marketing cards inside app screens.

### Color System

Use semantic tokens rather than raw component colors.

Recommended light theme direction:

- Background: warm off-white or paper-adjacent neutral, subtle enough to remain clean.
- Surface: near-white with a small warm cast.
- Surface raised: a slightly separated neutral for panels and sheets.
- Text: ink-like neutral with strong contrast.
- Muted text: warm gray, still accessible.
- Primary: subdued ink green or teal used for primary actions and focus.
- Accent: restrained amber for attention and pending states.
- Info: blue-gray for neutral automation and system information.
- Danger: restrained red used sparingly.
- Border: warm neutral divider stronger than the background but quieter than text.

Income and expense colors must not rely on red/green alone. Use signs, labels, icons, or direction indicators in
addition to color.

Dark theme should be designed intentionally, not created by simple inversion. Keep the warm identity through desaturated
neutral surfaces and accessible text contrast.

### Typography

Use a clear modern sans-serif family. Do not use handwritten fonts.

Typography priorities:

- 16px minimum for mobile body and inputs where native zoom is a risk.
- Tabular numbers for amounts, dates, counters, and chart labels.
- Right-aligned amount columns in dense entry rows.
- Quiet section headings, not hero-scale headings inside app panels.
- No negative letter spacing.

### Shape, Elevation, And Texture

- Use small-to-medium radius, generally 6px to 8px for controls and panels.
- Prefer borders and background contrast over shadows for ordinary surfaces.
- Reserve shadows for dialogs, popovers, menus, and task queue panels.
- Avoid nested cards. Sections should be bands or unframed layouts; cards should be reserved for repeated items,
  modals, and genuinely framed tools.
- Subtle ledger or receipt feeling can come from date separators, ruled group headers, compact index-like filters, and
  number alignment.

### Motion

Motion should be quiet and functional:

- 150ms to 250ms for hover, press, filter, sheet, and popover transitions.
- Transform and opacity only where possible.
- Respect `prefers-reduced-motion`.
- Avoid decorative loops, excessive springs, and choreographed page effects.

## Global Shell And Navigation

The workspace should feel like one stable app shell rather than separate pages with independent spacing.

Desktop:

- Use a calm top app bar with product identity, global status, and account menu.
- Keep the four workspace tabs visible near the top of the main work area.
- Use consistent max width and gutters across tabs, with content-specific width variants.

Mobile:

- Use bottom navigation for `stream`, `details`, `stats`, and `settings`.
- Keep touch targets at least 44px.
- Avoid putting primary actions too close to the gesture area without safe-area padding.

Global rules:

- Remove ledger switchers, ledger names as selectors, and any "current ledger" controls.
- Each tab should have one clear primary action or mode.
- Secondary and overflow actions belong in menus or local toolbars.
- Toasts are for short feedback.
- Dialogs are for decisions.
- Sheets or modals are for complex editing.
- The task queue is a global automation status surface.

## Tab Designs

### Stream

Stream is the fast capture and recent activity surface.

It should prioritize:

- quick entry;
- AI text or receipt input;
- recent source documents and entries;
- clear date grouping;
- task progress that is relevant to newly submitted items.

Entry rows should emphasize merchant or note, category, amount, and time. Use less ornamentation and stronger alignment.
Mobile should keep input, recent entries, and task state from competing in the same visual block.

### Details

Details is the organize and correct surface.

It should share row and detail primitives with Stream but use higher density and stronger tools:

- search;
- date range;
- category;
- account or payment source if present;
- currency;
- amount range;
- uncategorized, anomaly, and review filters;
- batch update and batch delete.

The toolbar, filter bar, selection model, and batch action bar should be extracted into shared components rather than
duplicated inside the tab.

Entry detail should feel like an editable ledger record:

- amount, direction, category, date, and account near the top;
- note, merchant, source document, original text, and AI parse details lower down;
- inline edit where practical;
- destructive actions in a low-emphasis danger area;
- clear unsaved-change protection.

### Stats

Stats is for understanding patterns, not for showing every possible chart.

The first view should summarize:

- month spending;
- month income;
- net amount;
- daily average;
- largest category;
- meaningful change or anomaly.

Recommended order:

1. Summary
2. Trend
3. Category structure
4. Ranking
5. Calendar or heatmap

Required cleanup:

- Move chart colors and heatmap colors to semantic tokens.
- Replace hardcoded currency symbols with a shared currency formatter.
- Provide empty states instead of returning nothing.
- Make tooltips reachable through keyboard and tap, not hover only.
- Increase mobile heatmap tap targets or adapt the heatmap into a touch-friendly weekly or monthly summary.
- Use accessible legends and avoid color-only meaning.

### Settings

Settings explains how the book works.

Use workflow grouping:

- Appearance and language: theme, language, currency display, date and number display.
- Bookkeeping rules: categories, accounts or payment sources, defaults, duplicate handling, uncategorized behavior.
- AI parsing: model-facing preferences, parsing language, field mapping, confidence handling, anomaly behavior.
- Automation: service credentials, API access, import/sync behavior, task queue preferences.
- Account and data: email, export, clear data, delete account, sign out.

Settings should not default every section to collapsed. Use either a left or top section navigation on larger screens,
and straightforward stacked sections on mobile.

Danger actions should be restrained and separated, not a large red zone that visually dominates the page. Category
management must not rely on hover-only controls.

## Shared Components

Create or standardize shared UI around these boundaries:

- `AppShell`
- `TopBar`
- `TabNavigation`
- `BottomTabNavigation`
- `EntryRow`
- `EntryListGroup`
- `EntryDetailSheet`
- `FilterBar`
- `FilterToken`
- `BatchActionBar`
- `StatsSummary`
- `ChartPanel`
- `SettingsSection`
- `SettingsField`
- `TaskQueuePanel`
- `EmptyState`
- `SkeletonBlock`
- form field primitives for amount, date, category, currency, and text

The goal is to shorten tab files and make them compositions of focused components.

## Login Design

The login page is part of the product experience, not a marketing page.

Production login:

- show Cashier identity;
- show a short, quiet description;
- show email OTP form states clearly;
- handle loading, error, resend cooldown, and verification steps;
- redirect to the root workspace after success.

Development login:

- when local dev bypass is enabled, show a subdued "Continue as dev" action.
- the action should not look like a production authentication option.
- explain only enough for a developer to understand that it opens a local dev session.

## Task Queue And Feedback

Task queue becomes a global automation status surface.

Desktop:

- a quiet status entry in the shell;
- expandable panel in the lower right or anchored near the status entry.

Mobile:

- bottom sheet or compact status row that respects safe-area padding.

The queue should show:

- active tasks;
- failures with retry paths;
- completion summaries when useful.

It should not spam normal success toasts. Failures must include cause and recovery action where possible.

## Accessibility And Interaction Requirements

- All icon-only buttons need accessible labels.
- Visible focus states are required.
- Keyboard order must match visual order.
- Controls must not rely on hover only.
- Touch targets should be at least 44px on mobile.
- Forms need visible labels and nearby error messages.
- Toasts should use polite live regions and not steal focus.
- Dialogs and sheets need focus management and escape routes.
- Reduced motion must be respected.
- Charts need legends, summaries, accessible tooltip interaction, and non-color-only encodings.

## Implementation Phases

This design should be implemented through a later plan in phases:

1. Establish design tokens, shared shell, root workspace routing, and single-ledger bootstrap.
2. Add local-only development access.
3. Unify Stream and Details rows, toolbars, detail sheet, and batch actions.
4. Rework Stats summary, chart colors, currency formatting, empty states, and mobile interactions.
5. Rebuild Settings around workflow groups and account-level automation.
6. Bring login, task queue, dialogs, forms, skeletons, and empty states into the new system.
7. Remove old ledger route generation, old multi-ledger UI language, and obsolete component styling.
8. Run responsive, accessibility, visual, and regression verification.

The implementation plan may split these into smaller commits, but it should preserve the product model from the first
phase so new UI does not continue to depend on route-level ledger ids.

## Test Strategy

Minimum behavior coverage:

- Authenticated root renders the workspace.
- Login success redirects to the root workspace.
- Historical `/ledger/[id]` URLs redirect to root and preserve tab/query state where practical.
- Workspace bootstrap resolves only the user's single default ledger.
- Legacy additional ledgers are not shown in navigation or settings.
- Service credentials are shown and managed as automation credentials.
- Development auth bypass is hidden without the flag.
- Development auth bypass is rejected in production.
- Development auth bypass provisions or reuses the dev user and opens the workspace.
- Stream, Details, Stats, and Settings tab parsing continues to work from root query params.
- Details filters and batch actions preserve state.
- Stats formatting uses the shared currency formatter.
- Settings groups render in the agreed order.

Minimum UI verification:

- 375px mobile viewport.
- 768px tablet viewport.
- Desktop wide viewport.
- Keyboard navigation through tabs, filters, dialogs, and settings.
- Reduced-motion behavior.
- Light and dark contrast checks for text, borders, charts, focus, and danger states.

## Risks

- The existing route structure and query cache keys are ledger-id oriented. Moving the user-facing app to root while
  keeping internal ledger scope requires a careful compatibility boundary.
- Some API and storage paths may still need ledger ids for tenant isolation and file ownership. The redesign should not
  remove internal scope ids prematurely.
- The visual redesign touches many shared surfaces, so token changes can create broad regressions if not staged.
- Development auth bypass is security-sensitive. It must be guarded by environment and runtime checks, and tests must
  prove production rejection.
- Legacy docs and PRD text currently describe multi-ledger behavior. They should be updated after the implementation
  plan lands or as part of the first implementation phase.

## Acceptance Criteria

- The user-facing product has no ledger switcher, ledger chooser, or multi-ledger settings.
- The app workspace is reached from root after login.
- New app links do not include `/ledger/[id]`.
- Historical ledger URLs redirect to the root workspace.
- Service credentials are presented as account-level automation for the single ledger.
- A local-only dev entry can open the workspace without Resend or OTP email setup.
- The dev entry cannot be used in production.
- Stream, Details, Stats, Settings, login, task queue, dialogs, forms, empty states, and skeletons share the same visual
  system.
- The visual system is warm, restrained, token-driven, accessible, and not ChatGPT-like.
- Mobile navigation and touch targets are comfortable.
- Stats uses token-driven chart colors, shared currency formatting, accessible tooltips, and explicit empty states.
- Settings uses the five agreed workflow groups.
